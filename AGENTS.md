# SynOS Architectural Contracts & AI Coding Agent Guardrails

> **CRITICAL DIRECTIVE FOR ALL AI CODING AGENTS & DEVELOPERS:**
> This repository houses **SynOS (Synthesized Lab Intelligence)**, a mission-critical hospital and diagnostic laboratory management system. Medical reports generated by SynOS serve legal, clinical, and diagnostic purposes.
> **DO NOT tinker, modify, or regress the architectural invariants outlined below.** Any proposed change to printing, PDF generation, or report templates must strictly adhere to these 7 Golden Rules.

## 🏛️ The 7 Invariant Rules of the SynOS Document Engine

### 1. Preprinted Mode is Strictly Explicit & Runtime-Only
* **Contract:** `isPreprinted` in [`ReportA4.jsx`](file:///src/SynOS.Frontend/src/features/documents/templates/ReportA4.jsx) MUST strictly evaluate `Boolean(forcePreprinted)`.
* **Prohibitions:**
  * **NEVER** fall back to `activeTemplate?.usePreprinted`. Database templates may contain `usePreprinted = true` flags that must NOT override digital letterhead display unless the user explicitly checks the box.
  * **NEVER** persist or read preprinted mode from `localStorage`. Preprinted stationery is a single-action user choice per print job, not a global terminal default.
  * Preprinted mode suppresses the digital background letterhead ONLY when the user explicitly checks the "PREPRINTED SHEET" toggle in the print UI or when `&preprinted=true` is explicitly provided in the URL query.

### 2. Cross-Browser Background Image Rendering (WebKit / Safari Native Engine)
* **Contract:** The report background letterhead (Sri Divya logo, top banner, center watermark-free emblem, bottom address bar) MUST be rendered using a standard HTML `<img />` tag with explicit physical dimensions:
  ```jsx
  <img 
    src={activeTemplate.backgroundPath} 
    alt="Report Background Letterhead"
    className="absolute inset-0 pointer-events-none select-none print:block" 
    style={{
      position: 'absolute',
      top: 0,
      left: 0,
      width: '210mm',
      height: '297mm',
      objectFit: 'fill',
      WebkitPrintColorAdjust: 'exact',
      printColorAdjust: 'exact'
    }}
  />
  ```
* **Prohibitions:**
  * **NEVER** convert this to a CSS `background-image` on a `<div>`. WebKit/Safari silently drops CSS background images when the native "Print backgrounds" checkbox is unchecked. HTML `<img>` elements with explicit dimensions are preserved by all browser engines.

### 3. Strict Zero Watermark Policy
* **Contract:** No report generated anywhere in SynOS shall contain any watermark text, image, overlay, or stamp.
* **Prohibitions:**
  * **NEVER** inject "DRAFT", "PROVISIONAL", "CONFIDENTIAL", or faded logos across reports.
  * This applies universally to: Typist Draft printouts, Pathologist review prints, Delivery Desk customer prints, WhatsApp shared links, and Backend Vector PDFs.

### 4. Signature Quad Contract (Lab Owner vs Consultant Pathologist)
* **Contract:** The report supports a dual-slot clinical authorization workflow:
  * **Slot 0 (Baseline / Lab Owner):** The Lab Owner (Chief Pathologist) is ALWAYS present by default as the baseline institutional authority.
  * **Slot 1 (Consultant / Reviewing Pathologist):**
    * **If Lab Owner signs digitally:** The Lab Owner is already in Slot 0; Slot 1 is NOT added.
    * **If an external Consultant Pathologist signs digitally:** Slot 1 contains their digital signature image, credentials, and verification stamp (dual signature).
    * **If a Typist prints for manual verification:** Slot 1 contains a physical blank ink signature line (`Verified By / Pathologist`) so the consultant can sign by hand with a physical pen.
* **Prohibitions:**
  * **NEVER** omit Slot 0.
  * **NEVER** place a digital signature on a Typist draft print.

### 5. Top-Anchored Test Headings & Demographics Alignment
* **Contract:** The investigation heading (e.g. `MRI NECK`, `COMPLETE BLOOD COUNT`) MUST be anchored directly below the Patient Demographics block at the top of the test content area.
* **Prohibitions:**
  * **NEVER** vertically center the test title or test content in the middle of the sheet.
  * Even for short or single-parameter tests, the content flows from the top margin downward.

### 6. Strict Single-Page A4 Sheet Dimension & Overflow Constraints
* **Contract:** An A4 sheet is physically `210mm` wide and `297mm` tall.
  * `#printable-report` and `.print-page-container` MUST remain locked to `width: 210mm; height: 297mm; overflow: hidden; page-break-after: avoid; break-after: avoid;`.
  * `@page` in CSS MUST specify `margin: 0 !important; size: A4 portrait;`.
  * `html, body, #root` in [`index.css`](file:///src/SynOS.Frontend/src/index.css) MUST retain `overflow: visible !important;` so Safari/WebKit does not render a blank white page in print preview.
* **User Advice for Safari:**
  * In Safari's native print sheet, users must keep **"Print headers and footers" unchecked** so Safari does not inject 24mm of browser margins that slice the footer bar onto a second page.

### 7. 100% Visual Parity Between Frontend Print & Backend PDF (WhatsApp Links)
* **Contract:** The backend PDF generation engine ([`QuestPdfReportRenderer.cs`](file:///src/SynOS.Services/QuestPdfReportRenderer.cs)) and the frontend browser print engine ([`ReportA4.jsx`](file:///src/SynOS.Frontend/src/features/documents/templates/ReportA4.jsx)) MUST remain 100% visually unified.
* WhatsApp report downloads and direct browser printouts must display identical coordinates, typography, spacing, and signature placements.

## 💰 Section II: Reception, Financials & Payer Mode Invariants (Production Shield)

### 1. Three Canonical Payer Modes & Immutable Lingo
The reception intake pipeline operates on three distinct, production-locked billing modes in [`MultiPayerPanels.jsx`](file:///src/SynOS.Frontend/src/features/reception/components/MultiPayerPanels.jsx):
* **Mode 1 (`Standard`):** `Direct / Standard`
  * Subtitle: `Desk collection & standard tariff` | Badge: `Retail`
  * Financial Contract: Billed directly to patient at desk. Patient pays cash/UPI/card.
* **Mode 2 (`PrepaidPartner`):** `Corporate B2B (Prepaid)`
  * Subtitle: `B2B partner billed, ₹0 at desk` | Badge: `B2B Prepaid`
  * Financial Contract: The patient pays ₹0 at the desk because the referral partner/hospital collects in advance. The lab bills the B2B referral partner monthly.
  * **PROHIBITION:** NEVER rename this mode to "Doctor", "Doctor B2B", or confuse it with Insurance. It represents Corporate & B2B Referral Partner contracts.
* **Mode 3 (`Insurance`):** `Insurance / TPA`
  * Subtitle: `Cashless pre-auth claim` | Badge: `Cashless`
  * Financial Contract: Cashless insurance pre-auth claims with potential co-pay.

### 2. Concession & Discount Defaults (Clinical Desk Rule)
* **Default Mode:** Custom discounts in [`BillingSummary.jsx`](file:///src/SynOS.Frontend/src/features/reception/components/BillingSummary.jsx) MUST default to **`FLAT` (`₹ Flat`)**, not `PERCENTAGE`.
* **Clinical Truth:** In clinical diagnostic desk workflows, receptionists enter flat rupee amounts (₹50, ₹100, ₹200). Defaulting to percentage turns a ₹100 concession into 100% off, wiping bills to ₹0.
* **Calculation Safeguards:**
  * Entering flat `100` on a ₹600 bill MUST yield `Gross: ₹600`, `Discount: -₹100`, `Net Bill: ₹500`.
  * Live deduction and Net Bill preview MUST be rendered beneath the input before the user confirms.
  * Backend calculations are enforced by [`RevenueEngine.cs`](file:///src/SynOS.Services/Revenue/RevenueEngine.cs) and verified by [`ProductionValidationTests.cs`](file:///tests/SynOS.Tests/ProductionValidationTests.cs).

### 3. Strict Boundary Defense (Zero Unsolicited Edits)
* **PROHIBITION:** When working on features such as expenses, inventory, prints, reports, or visual facelifts, AI agents and developers are **FORBIDDEN** from touching:
  * Payer mode definitions, IDs, or labels in `MultiPayerPanels.jsx`
  * Financial formulas, discount default states, or net bill calculations in `BillingSummary.jsx`
  * Invariants in `RevenueEngine.cs`
* Every PR/commit touching billing or revenue must pass `dotnet test tests/SynOS.Tests/SynOS.Tests.csproj --filter "ProductionValidationTests"`.

### 4. Canonical Total Patient Intake (Walk-Ins) Metric Invariant (Zero-Regression Rule)
* **Clinical Contract:** In clinical hospital and diagnostic lab operations, Card 1 (`Walk-Ins`, qualifier `Paid/Credit`) represents the **front-door physical patient volume** across all desks in the branch for today.
  * Every confirmed patient who receives an official accession token (`MAI-xxx`), is not an uncommitted draft (`v.Status != Draft` and `!v.Token.StartsWith('D-')`), and has not been cancelled (`v.Status != Cancelled`) MUST be counted in `WalkInsToday`.
  * **PROHIBITION:** NEVER subtract, exclude, or strip Corporate B2B (Prepaid) referral visits or desk credit (Full Due) visits from `WalkInsToday`. Physical humans do not vanish from the clinic simply because their bill is settled by a corporate partner or billed on credit. B2B financial accounting is tracked independently in Tile 5 (`Prepaid Bills Issued`).
  * In `ReceptionScreen.jsx`, Card 1 must retain double-layered fallback resilience: if `summary.walkInsToday` is 0 but confirmed tokens exist in `todayNonDraftQueue`, it seamlessly renders the active queue length.

### 5. Action Queue Payment Semantics & Corporate B2B Protection Invariant (Zero-Pollution Rule)
* **Clinical Contract:** The Action Queue (`ReceptionScreen.jsx`) table represents the real-time front-desk ledger. The `PAYMENT` column must strictly observe the canonical 6-state hierarchy:
  1. `DRAFT`: Uncommitted visits with temporary tokens (`D-xxx`).
  2. `PREPAID`: Corporate B2B referral visits billed to partner accounts (`PaymentCollectionModel == "PartnerCollects"` or `BillingType == PrepaidPartner`).
     - Subtext MUST display the referring doctor/partner name (`row.referrerName`).
     - **PROHIBITION:** NEVER overwrite or hijack `PREPAID` visits with `OVERPAID`, `REFUND DUE`, or desk cash alerts. Corporate partner bills are settled via B2B receivables, not desk counter refunds.
  3. `OVERPAID`: Applies STRICTLY and ONLY to retail direct desk collections (`!isPrepaid && !isDraft`) where physical money collected exceeds the revised bill total (`totalPaid > totalBilled`).
  4. `PARTIAL DUE`: Active retail visits with partial desk payments (`totalPaid > 0 && remainingDue > 0`). Displays `remainingDue` in main text with green `Paid: ₹{totalPaid}` subtext.
  5. `FULL DUE`: 100% counter credit visits (`totalPaid === 0 && remainingDue > 0`). Rendered in pastel orange (`bg-orange-500/15 text-orange-700`).
  6. `PAID` / Method: Fully cleared desk visits (`Cash`, `UPI`, `Card`).
* **PROHIBITION FOR AI CODING AGENTS & DEVELOPERS:**
  - **DO NOT** alter the order of this evaluation chain.
  - **DO NOT** omit `!isPrepaid` from `isOverpaid`.
  - **DO NOT** inject ad-hoc refund or collection notices that distort B2B partner attribution.

## 🏛️ Section III: Finance Hub Truth Engine & Ledger Parity Invariants (The 8 Canonical Tabs)

The Finance Hub (`RevenueScreens.jsx`) houses the ultimate diagnostic and legal truth of all clinical revenue, cash drawers, and partner receivables across 8 canonical tabs:
1. `Bills & Collections`
2. `Due Bills`
3. `Pending Receivables`
4. `Visit Corrections`
5. `Cancellations & Refunds`
6. `Due Change & Patient Refunds`
7. `Collection History`
8. `Cash Drawer Shift Ledgers` (`#POS-DRAWER`)

### 1. The Cash Drawer & Collection History 100% Parity Contract
* **Invariant:** Any physical cash transaction attributed to a cashier in `Collection History` MUST appear in `Cash Drawer Shift Ledgers` for that same cashier and date range. The net cash in hand target must match the drawer ledger to the paisa.
* **Cashier Attribution Hierarchy:**
  - AI agents and developers MUST NOT restrict cashier matching to a single raw field like `p.ReceivedByUserId == effectiveUserId`.
  - Cashier identification MUST consistently observe the canonical 4-tier attribution hierarchy:
    ```csharp
    p.ReceivedByUserId == effectiveUserId 
    || p.Invoice.Visit.AssignedReceptionistId == effectiveUserId 
    || p.Invoice.Visit.CreatedByUserId == effectiveUserId
    ```
  - When visits are confirmed under an admin/station token while a receptionist created the visit, the transaction belongs to the receptionist's shift cash drawer.

### 2. Multi-Branch Safe Scoping (Anti-Drop Invariant)
* **Invariant:** Never use blind single-branch user fallbacks (e.g. `UserBranchRoles.FirstOrDefault().BranchId`) to filter drawer payments.
* **Prohibitions:**
  - If a query does not explicitly receive a valid `branchId`, or when `All Branches` / consolidated mode is active, the query MUST NOT discard transactions with null branch IDs or alternate branch IDs.
  - Applying an unverified branch filter drops legitimate transactions and wipes cash drawer ledgers to zero.

### 3. Dual-Ledger Synchronization (`Payments` vs `RevenueFacts`)
* **Invariant:** Operational payments (`dbo.Payments`) and immutable accounting facts (`dbo.RevenueFacts`) MUST remain in lockstep.
* **Rule:** Any operation that deletes, voids, cancels, or switches a payment mode (such as converting a Cash visit to Corporate B2B Prepaid in `VisitService.cs`) MUST explicitly declare a `Reversal` fact in `RevenueFacts`.
* **Prohibition:** NEVER delete from `dbo.Payments` without declaring the corresponding reversal fact. Orphaned facts create phantom cash liabilities in `Collection History`.

### 4. Zero-Tolerance Regression Shield for Finance Tabs
* **Invariant:** Whenever an AI agent or developer modifies any file touching billing, invoices, payments, revenue facts, or finance screens:
  - You MUST verify that changes do not break or zero out any of the other 7 tabs.
  - You MUST NOT introduce ad-hoc SQL filters or property path mutations without verifying frontend DTO consumption.

### 5. Branch Switching Architecture: Admin Oversight vs Multi-Branch Staff Invariant
* **Admin Users:** Possess global cross-facility oversight. Admins can switch branches on the fly directly inside the Finance Filter Bar (`All Branches` consolidated view or single branch dropdown in `StandardFilterBar.jsx`) without altering their terminal's global operating facility.
* **Non-Admin Multi-Branch Users (Receptionists, Phlebotomists, Lab Techs):** Strictly restricted from in-page consolidated multi-branch switching in the Finance Hub. They are bound to one active facility at a time. Staff with multi-branch access must switch their working facility globally from the top navigation bar (`SystemBar.jsx`), which updates their active facility context for the entire application.

## 🛠️ Build & Verification Protocol

When making modifications to the frontend or document pipelines:
1. Rebuild the frontend bundle:
   ```bash
   cd src/SynOS.Frontend && npm run build
   ```
2. Copy `dist-build/*` into `src/SynOS.Api/wwwroot/`.
3. Clean up stale asset hash files in `src/SynOS.Api/wwwroot/assets/`.
4. Verify backend build:
   ```bash
   dotnet build src/SynOS.Api
   ```
5. Test both:
   * Direct Web Print (`/print/report/:id?forceLive=true`)
