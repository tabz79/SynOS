### Step 3A-4: Idempotency Anchor Design

This document evaluates two options for ensuring the "Commission Recognition" event is idempotent and recommends a final design for implementation.

#### **1. Evaluation of Option A: `PayableFact` as Idempotency Anchor**

This approach uses a fact generated by the commission recognition event itself as the key for idempotency.

*   **Mechanism:** Before initiating the commission recognition process for a given `PaymentId`, the system would first query the `PayableFacts` ledger to check if a record linked to that specific `PaymentId` already exists.
*   **Pros:**
    *   **Direct & Unambiguous:** The check is direct: "Has a liability for this specific payment already been recorded?" This eliminates any ambiguity.
    *   **Domain-Specific:** The idempotency of the referral commission system is controlled by its own internal facts. It has no dependency on the implementation details or data conventions of the separate Revenue Engine.
    *   **Robust:** This method is resilient to any future changes in how `RevenueFact`s are created or referenced.
*   **Cons:**
    *   **Requires Schema Change:** This approach requires adding a new field (e.g., `SourcePaymentId`) to the `PayableFact` entity to create the direct link to the payment event.

#### **2. Evaluation of Option B: `RevenueFact` as Idempotency Anchor**

This approach uses the pre-existing `RevenueFact` as the primary key for idempotency.

*   **Mechanism:** Before initiating commission recognition, the system would first confirm that a `RevenueFact` exists where `SourceReferenceId` matches the `PaymentId`. It would then have to perform a *second* check to ensure a `PayableFact` for that event hasn't *also* been created, leading to complex `(IF A exists) AND (IF B does NOT exist)` logic.
*   **Pros:**
    *   Leverages an existing entity that is already a precondition for the trigger.
*   **Cons:**
    *   **Tight Coupling:** It tightly couples the Referral system's correctness to the `RevenueEngine`'s internal data conventions. If the method for creating `RevenueFact`s changes how it uses `SourceReferenceId`, the referral idempotency logic will silently break.
    *   **Indirect & Brittle:** It does not directly answer the question "Has commission for this payment already been processed?". It only answers "Has revenue for this payment been recorded?". This is an indirect and less reliable signal for idempotency.
    *   **Violates "No Assumed Guarantees":** As established in the prior audit, it is not currently guaranteed that `RevenueFact.SourceReferenceId` is always populated with the `PaymentId`. Relying on it would be based on an unverified assumption.

#### **3. Recommendation and Justification**

**Recommendation:** **Option A (`PayableFact` as Anchor)** is unequivocally recommended.

*   **Justification:** Architectural soundness and robustness are paramount for financial systems. Option A makes the commission recognition process self-contained and responsible for its own idempotency. The check is simple, direct, and immune to changes in other parts of the system. The cost of a minimal, additive schema change is negligible compared to the long-term risk and complexity of creating a tight, brittle dependency between two separate financial engines (Option B).

#### **4. Required Minimal Change**

The implementation of the recommended option requires a single, additive schema change:

*   **Entity:** `PayableFact`
*   **Field to Add:** A new field, `SourcePaymentId` (type `Guid`, indexed for fast lookups), must be added. This field will store the `PaymentId` of the payment event that triggered the commission recognition.
